The native checkbox and radio button elements don't offer much in terms of styling (aside from `accent-color`),
and they can be tricky to customize without compromising accessibility.

You essentially have to hide the native control and visually rebuild it from scratch. However, if done correctly,
you can preserve its functionality and avoid having to handle all the accessibility work yourself.

<aside class="callout" aria-label="Disclaimer">
  To keep things focused, I won't be covering the `<label>` element. I'll assume you will use it properly
  and keep it associated with the `<input>` element, either by wrapping it or by using the `for` attribute.
</aside>

## Hide the default

Beware of the way in which you hide the controls! You might be tempted to reach for `display: none`,
but that's more drastic than it seems: it will completely remove the controls from the accessibility tree.

There are other ways that would work just fine, but your safest bet is to use `appearance: none` nonetheless,
which exists precisely for this purpose (along with `margin: 0`, which is not reset by it).

```css
input[type="checkbox"],
input[type="radio"] {
  appearance: none;
  margin: 0;
}
```

Perfect! Now that we have a clean slate to work with, let's start!

## Styling the controls

To build them, we'll first style the `<input>` elements to recreate the "box" of the controls
and then use some pseudo-elements to draw the checkmark and the dot glyphs.

### The input

```css
input[type="checkbox"],
input[type="radio"] {
  --control-color: var(--foreground);

  appearance: none;
  margin: 0;
  position: relative;
  width: 1.25rem;
  aspect-ratio: 1;
  flex-shrink: 0;
  border: 1px solid var(--control-color);
  background-color: var(--background);

  &:hover {
    background-color: var(--background-hover);
  }

  &:disabled {
    background-color: var(--background-disabled);
    --control-color: var(--foreground-disabled);
  }
}
```

Nothing special here, just some basic styling:

- The `--control-color` variable keeps the glyphs and the border in sync (we'll see it come in handy later).
- `position: relative` to position the pseudo-elements.
- `flex-shrink: 0` is a little bonus that prevents the controls from shrinking when they're placed inside a flex container.

### The pseudo-elements

First, the setup:

```css
input[type="checkbox"],
input[type="radio"] {
  /* ... */

  &::after {
    content: "";
    position: absolute;
    inset: 0;
    margin: auto;
    aspect-ratio: 1;
    background-color: var(--control-color);
    display: none;
  }

  &:checked::after {
    display: block;
  }
}
```

Then the specific styles for the glyphs:

```css
input[type="checkbox"] {
  border-radius: 0.125rem;

  &::after {
    --checkmark-clip: polygon(84.5% 8.3%, 37.5% 56.5%, 15.6% 35.2%, 0 50.7%, 37.5% 91.7%, 100% 16.7%);

    width: 0.875rem;
    clip-path: var(--checkmark-clip);
  }
}

input[type="radio"] {
  border-radius: 100vmax;

  &::after {
    width: 0.625rem;
    border-radius: 100vmax;
  }
}
```

The checkmark is created using a `clip-path`, but you could easily swap it for a `mask` with any `<svg>` you want instead:

```css
input[type="checkbox"] {
  /* ... */

  &::after {
    --checkmark-icon: url('data:image/svg+xml,<svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24"><path d="M20.285 2l-11.285 11.567-5.286-5.011-3.714 3.716 9 8.728 15-15.285z"/></svg>');

    /* ... */
    mask: var(--checkmark-icon) center / contain no-repeat;
  }
}
```

Both of these approaches let you easily control the element's color, whereas something like `background-image` wouldn't.

But why is this so important?

## Forced-colors mode

In forced-colors mode, none of the colors you've set matter, and any element that relies on color for legibility can be heavily compromised.
Most backgrounds are removed, and our pseudo-elements are no exception: you can say goodbye to our glyphs!

But there's a solution: just use the <Link href="https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/system-color">system colors</Link> yourself!

Remember the `--control-color` variable? Now it comes into play.

```css
input[type="checkbox"],
input[type="radio"] {
  /* ... */

  @media screen and (forced-colors: active) {
    &:checked {
      --control-color: Highlight;
    }

    &:disabled {
      --control-color: GrayText;
    }
  }
}
```

Easier then expected, right? But don't mess with them, or you'll make a disservice to the users relaying on them.
Choose the ones already used by the native controls you're trying to reproduce (just as I did).

And one last thing...

## Print

Poor `background-color` isn't safe in print mode either! The browser might remove it to save ink.

We could <Link href="https://dev.to/alvaromontoro/comment/1214h">use `box-shadow` instead</Link>,
but that's a bit of a hack, and it wouldn't preserve the glyphs in forced-colors mode anyway.

The right way to prevent this is to use `print-color-adjust: exact`.

```css
input[type="checkbox"],
input[type="radio"] {
  /* ... */

  print-color-adjust: exact;
}
```

That will tell the browser to print the element as it appears on screen. Use it sparingly!
As always, overriding browser behavior or user preferences comes with great responsibility.

## Conclusion

The key takeaways are two: preserve the native `<input>` for its built-in behavior and accessibility,
and remember to account for unusual environments, such as forced-colors mode and print.

Until next time, be (and code) well!
